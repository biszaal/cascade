# On-device UI tests

These cover the two things a browser preview and a unit test cannot: **real taps on a
device** and **device rotation**.

They drive the installed app by bundle id rather than hosting it, so this is a standalone
test bundle and does not need to live inside the Expo-generated Xcode project (which is
regenerated by every prebuild).

The tests find lanes through the **accessibility labels the app already exposes** - the
same strings a screen reader reads. So the automation and the accessibility work verify
each other: if a lane stops describing itself, these tests stop being able to tap it.

## Running

```
npm start            # Metro - the debug build fetches its bundle at launch
npm run ios          # build and install onto a simulator
./e2e/run.sh         # all tests on the first booted simulator
./e2e/run.sh <udid> testE_orientationContract
```

`brew install xcodegen` is required; the `.xcodeproj` is generated and not committed.

## What each test proves

| Test | Proves |
|---|---|
| `testA_enterLevel` | The home screen loads and its primary action reaches a board; lanes carry accessibility labels. |
| `testB_pourChangesMoveCount` | A real two-tap pour registers as one move - Undo goes from disabled to enabled. |
| `testC_rotationRelaysOutTheBoard` | Rotating does not clip or empty the board, and the HUD survives. |
| `testD_dailyBoardSurvivesRotation` | Nine lanes stay present and reachable across a rotation, exercising the one-row / two-row decision that a five-lane level cannot. |
| `testE_orientationContract` | **iPad rotates to landscape; iPhone stays portrait.** This is the only way to prove the per-idiom `Info.plist` orientation keys actually work. |

Run `testE` on both a phone and a tablet - it asserts the opposite outcome on each.
